# SQL Server: a script that ends its transaction without an error is recorded as applied

## Problem
On SQL Server a script can end the transaction it runs in without raising an error: `if @@trancount > 0 rollback` in the script (scripts generated by Redgate tools have it), or a procedure it calls whose `CATCH` block rolls back and swallows the error. `Transaction.Current` stays `Active` then, and the commands after the rollback run in autocommit mode and are committed at once (`MsSqlDA.IsTransactionUsableAsync` documents this; verified for SQL tests in 0096-76 and for failed code files in 0096-61).

Only two callers check for it: `UnitTestItemRunner` after every SQL test, and `CodeItemDeployer` after a code file that failed. Nothing checks after a script that succeeded. From the code, not reproduced:

- **A migration or breaking script, `TransactionWrapLevel: Migration` (the default).** The statements before the `ROLLBACK` are undone. The rest of the script and `UpdateMigrationStateAsync` run in autocommit mode and are committed. The commit of the scope then fails, so the deployment fails, but `dblive.migration` says `applied`, and the next deployment skips a migration that is applied in part.
- **`TransactionWrapLevel: Deployment`.** The same, and everything the deployment runs after that script (later migrations, code files, AfterDeploy scripts and their rows) is committed too, while the scripts before it are rolled back.
- **BeforeDeploy and AfterDeploy scripts, and code files that succeed,** inside the deployment transaction: the same gap.
- **A code file in its own transaction** (0096-83): it already fails, on `commit transaction` with the error 3902 of SQL Server, and is not marked `applied`. But its batches after the `ROLLBACK` stay committed, and the error does not say what happened.

With `TransactionWrapLevel: None` a script has no transaction to end, so it is not affected.

It is the only finding of the code review of 2026-11-17 (finding 1) that leaves a database in a wrong state without saying so.

## Where
- `src/DbLive/Deployers/Migrations/MigrationItemDeployer.cs:97-113` (the script, then the `applied` row, no check between them)
- `src/DbLive/Deployers/Folder/FolderDeployer.cs:55-80`
- `src/DbLive/Deployers/Code/CodeItemDeployer.cs:21-40` (the check runs only in the `catch`, `:51-53`)
- `src/DbLive.MSSQL/MsSqlDA.cs:192-226` (`ExecuteScriptAsync`: every script of a deployment goes through it), `:16-22` (`IsTransactionUsableAsync`)
- `src/DbLive/Deployers/Testing/UnitTestItemRunner.cs:58-67` (the existing check after a test)

## Fix
One check in `MsSqlDA.ExecuteScriptAsync` covers every caller: when the script ran in a transaction (`Transaction.Current` is set, or `ownTransaction`), read `@@trancount` on the connection of the script after its batches. When it is 0, throw a `DbLiveSqlException` that says the script ended its transaction, that the statements after it are committed, and what to change in the script. The callers already turn a `DbLiveSqlException` into `MigrationDeploymentException`, `FolderDeploymentException` or `CodeDeploymentException` with the path of the file, and do not write the `applied` row.

The statements that ran after the `ROLLBACK` are committed and cannot be undone. The fix makes the deployment fail with the file and the cause, and keeps the script from being recorded as applied.

- [ ] Check after every batch, to stop at the first batch that ended the transaction, or once after the file? After every batch costs one more round trip per batch.
- [ ] A script that runs `ROLLBACK` and then `BEGIN TRANSACTION` leaves `@@trancount` at 1, in another transaction. Compare `current_transaction_id()` before and after the script instead? (The function exists since SQL Server 2016: from memory, not verified.)
- [ ] PostgreSQL: does a top-level `rollback;` or `commit;` in a script end the ambient transaction without an error? Not checked. `PostgreSqlDA.IsTransactionUsableAsync` runs `select 1` and sees only an aborted transaction (`25P02`), not one that ended.
- [ ] `COMMIT` in a script ends the transaction as well. The same error, or a message of its own?
