# A script that ends its transaction without an error is recorded as applied

## Problem
On SQL Server a script can end the transaction it runs in without raising an error: `COMMIT` or `ROLLBACK` in the script itself, such as `if @@trancount > 0 rollback` (scripts generated by Redgate tools have it: see Notes). A procedure that ends the transaction of its caller, such as one whose `CATCH` block rolls back and swallows the error, is not silent: SQL Server fails the script with Msg 266 when the procedure returns, and the migration is not recorded as applied; the statements of the script after the call stay committed (verified, `ScriptEndsTransactionTests.Migration_whose_procedure_ends_its_transaction_fails_with_error_266`). `Transaction.Current` stays `Active` then, and the commands after the rollback run in autocommit mode and are committed at once (`MsSqlDA.IsTransactionUsableAsync` documents this; verified for SQL tests in 0096-76 and for failed code files in 0096-61).

Only two callers check for it: `UnitTestItemRunner` after every SQL test, and `CodeItemDeployer` after a code file that failed. Nothing checks after a script that succeeded. Verified on SQL Server 2025 (`ScriptEndsTransactionTests`, see Notes):

- **A migration or breaking script, `TransactionWrapLevel: Migration` (the default).** The statements before the `ROLLBACK` are undone. The rest of the script and `UpdateMigrationStateAsync` run in autocommit mode and are committed. The commit of the scope then fails with the error 3902 (`MigrationDeploymentException` "Unexpected error deploying ..." with `TransactionAbortedException` inside), but `dblive.migration` says `applied`, and the next deployment succeeds and skips a migration that is applied in part.
- **A migration under `TransactionWrapLevel: Deployment`.** The `ROLLBACK` also undoes the rows that this deployment saved for its migrations (`MigrationsSaver`), so `UpdateMigrationStateAsync` finds no row: `MigrationDeploymentException` with `DbLiveMigrationItemMissedSqlException` ("Migration item not found"). The statements after the `ROLLBACK` stay committed, and the next deployment runs the script again on top of them.
- **BeforeDeploy and AfterDeploy scripts, and code files that succeed,** inside the deployment transaction: everything after the `ROLLBACK` is committed (the rest of the script, the code files after it, AfterDeploy, and their rows in `dblive.code` and `dblive.folder_items`), while the deployment fails on its commit with a bare `TransactionAbortedException` (3902) that names no file. A code file that ended the transaction is marked `applied` without its batches before the `ROLLBACK`, and the next deployment skips it by its hash: the objects of those batches are never created.
- **A code file in its own transaction** (0096-83): it fails on `commit transaction` with the error 3902 and is marked `error`, but its batches after the `ROLLBACK` stay committed, and the error does not say what happened. When another file of the round succeeds, the file is retried in the next round on top of what it left, and the error of the retry is the one reported.

With `TransactionWrapLevel: None` a script has no transaction to end, so it is not affected. Neither is a code file with In-Memory OLTP DDL outside the deployment transaction: since 0096-88 it runs without a transaction of its own.

**PostgreSQL is affected too** (verified, `ScriptEndsTransactionExploreTests`, see Notes): a top-level `rollback;` or `commit;` in a script ends the ambient transaction without an error, and the statements after it run in autocommit mode. A migration under `Migration` is recorded as `applied` and skipped by the next deployment, as on SQL Server; the commit of the scope fails with `TransactionInDoubtException` ("This NpgsqlTransaction has completed"). Under `Deployment` a migration fails with "Migration item not found", and a code file with `25P01: RELEASE SAVEPOINT can only be used in transaction blocks`; what ran after the end of the transaction stays. `PostgreSqlDA.IsTransactionUsableAsync` (`select 1`) does not see an ended transaction: `select 1` succeeds in autocommit mode.

It is the only finding of the code review of 2026-11-17 (finding 1) that leaves a database in a wrong state without saying so.

## Fix
One check in `MsSqlDA.ExecuteScriptAsync` covers every caller: when the script ran in a transaction (`Transaction.Current` is set, or `ownTransaction`), read `@@trancount` on the connection of the script after its batches. When it is 0, throw a `DbLiveSqlException` that says the script ended its transaction, that the statements after it are committed, and what to change in the script. The callers already turn a `DbLiveSqlException` into `MigrationDeploymentException`, `FolderDeploymentException` or `CodeDeploymentException` with the path of the file, and do not write the `applied` row.

On PostgreSQL the same check goes to `PostgreSqlDA.ExecuteNonQueryAsync`, when `Transaction.Current` is set (see the question below). `CodeItemDeployer` must then not retry a file that failed with this error without asking `IsTransactionUsableAsync`: on PostgreSQL it returns `true` after the end of the transaction.

The statements that ran after the `ROLLBACK` are committed and cannot be undone. The fix makes the deployment fail with the file and the cause, and keeps the script from being recorded as applied.

- [ ] Check after every batch, to stop at the first batch that ended the transaction, or once after the file? After every batch costs one more round trip per batch.
- [ ] A script that runs `ROLLBACK` and then `BEGIN TRANSACTION` leaves `@@trancount` at 1, in another transaction. Compare `current_transaction_id()` before and after the script instead? (The function exists since SQL Server 2016: from memory, not verified. DbLive requires SQL Server 2017 or later.) For the tests the maintainer decided on 2026-11-15 in 0096-76 that the comparison is not worth one more query.
- [x] PostgreSQL: does a top-level `rollback;` or `commit;` in a script end the ambient transaction without an error? Not checked. `PostgreSqlDA.IsTransactionUsableAsync` runs `select 1` and sees only an aborted transaction (`25P02`), not one that ended. Answered by an experiment (2026-11-17): yes, see Problem and Notes.
- [ ] PostgreSQL has no `@@trancount`. Compare `transaction_timestamp()` read on the connection of the script before and after it? It is the same value in one transaction, and a later one in the transaction that a command after the end of the ambient one runs in. One more query per script, two in all.
- [ ] PostgreSQL, a code file outside the deployment transaction: it is one command, one implicit transaction. `rollback;` in it ends that transaction: the statements before it are undone, the file is marked `applied`, and the deployment succeeds (verified: `v1` is never created). It is not a transaction of DbLive, like a script under `None`, but the docs promise that a code file is applied as a whole. Leave it, or run such a file between `begin` and `commit` of its own, as on SQL Server, to check it?
- [ ] `COMMIT` in a script ends the transaction as well. The same error, or a message of its own?
- [ ] A code file in its own transaction that ended it: return `CanRetry = false`, so that the next round does not run it again on top of what it left and replace its error? The deployment then fails at once, and the other files of the round are not deployed.
- [ ] PostgreSQL, SQL tests: a test whose own script runs `commit;` or `rollback;` passes and leaves its data behind, the same bug as 0096-76 on SQL Server (verified 2026-11-17: `insert 100; commit; insert 200;` passes, and both rows stay; with `rollback;` the row 200 stays). The check after the test, `IsTransactionUsableAsync` (`select 1`), does not see it. The docs speak of procedures only (`docs/llms-full.txt` §8.2 and §16, `docs/unit-testing/index.md` "Code that rolls back the transaction": a procedure cannot end the transaction of its caller, `2D000`), and say nothing of `commit` in the test itself. Fix it here with the check of PostgreSQL above, or in a task of its own? A test that passed would fail: `breaking: true`, as 0096-76.

- Both tables checked again on `e0e95b6` (0096-88): the same results. 0096-88 runs a SQL Server code file with In-Memory OLTP DDL without a transaction of its own outside the deployment transaction: the check of the fix does not apply to it, as to a script under `None`.
- 2026-11-17, considered: own transactions (`SqlConnection.BeginTransaction`, `NpgsqlConnection.BeginTransaction`) instead of `TransactionScope`. Decision of the maintainer (2026-11-17): not taken, and no idea file for it: the statements after the end of the transaction are committed with either, and what it would improve does not pay for rewriting the data access of both providers. Verified with a temporary test on one connection, not kept:
  - The statements of the script after its `COMMIT` or `ROLLBACK` are committed with either: the server runs them in autocommit mode, whatever the client does.
  - SQL Server: the `SqlTransaction` becomes a zombie at once, `tx.Connection` is `null`, without a query: after `rollback`, `commit`, `rollback; begin transaction` and an error under `XACT_ABORT ON`; not after a nested `begin transaction ... commit`, a rollback to a savepoint or an error that leaves the transaction open. The next commands on that connection, with the transaction or without it, run in autocommit mode without an error, and `Commit()` throws "This SqlTransaction has completed". So DbLive would still check before its commands, but by a property instead of a query.
  - PostgreSQL: after `rollback;` or `commit;` Npgsql refuses the next command with the transaction (`InvalidOperationException` "Transaction is already completed"), so the row `applied` could not be written. It has no public property for it (`IsCompleted` is internal), and after `rollback; begin;` it does not notice anything: the new transaction of the script is committed.
  - A procedure that ends the transaction of its caller fails the script with Msg 266 ("Transaction count after EXECUTE indicates a mismatching number of BEGIN and COMMIT statements"), so the case of the Problem with a procedure that swallows the error is not silent: the script fails, and its statements after the call stay committed. A `COMMIT` or `ROLLBACK` in the script itself is the silent case. The same under `TransactionScope` (the last row of the SQL Server table).
- The claim of the Problem that scripts generated by Redgate tools have `if @@trancount > 0 rollback`: from memory their deployment script runs it only after an error, and DbLive stops at the first batch that fails, so such a script would not end the transaction silently. Not verified.
