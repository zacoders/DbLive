# PostgreSQL: a SQL test cannot read a value of a composite type

## Release note
**PostgreSQL: a SQL test that cannot read a value names it and says what to do.** DbLive reads every value of every result set of a SQL test, and Npgsql cannot read some of them: a composite type (a column, or `select f()` of a function that returns one), the row of a table, `regclass` and the other `reg*` types but `regtype` and `regconfig`, `pg_snapshot`, a `numeric` `NaN` or infinity, an `interval` with months or years, a date after the year 9999. The test failed with the error of Npgsql alone, such as `Reading as 'System.Object' is not supported for fields having DataTypeName 'public.pair'`. Now it fails with `Cannot read the value of the column 'p' in row 1 of result set 1, of the type public.pair: <the error of Npgsql>` and `Select the value as text in the test.` The docs list these values and how to select them: as text (`p::text`), a composite value also as its fields (`(p).*`). Nothing to change on upgrade.

## Problem
A SQL test that selects a column or a value of a composite type (`create type pair as (a int, b text)`) fails with `InvalidCastException: Reading as 'System.Object' is not supported for fields having DataTypeName 'public.pair'`, with any assert and without one: DbLive reads every value of every result set. Verified on 2026-11-24 with Npgsql 10.0.1 and `postgres:18`, the type known to the data source (a test run in a process without the deployment, and after `ReloadTypesAsync`): a table column `p pair` and `select row(1,'x')::pair as p` both fail. An anonymous record (`select row(1, 'x') as r`) reads.

Npgsql reads a composite type only when it is mapped to a .NET type (`MapComposite<T>()`). `EnableUnmappedTypes()` does not cover composite types: with it the read fails the same way (verified, see Notes). DbLive opens its connections with `new NpgsqlConnection(connectionString)`.

`docs/llms-full.txt` §8.3 says nothing of composite types. It names other values that cannot be read (an `interval` with months, a `numeric` `NaN`) and says to cast them to `text` in the test.

## Fix
- [x] Docs only: the value cannot be read, cast it to `text` in the test or select its fields (`(p).a`)? Check what the text of a composite value is and that `rows` compares it. The text is the one of PostgreSQL: `(1,x)`, and `(,"a ""b"", c")` for a NULL field and a text with a quote and a comma. `rows` compares it as a string, `rows-with-schema` has `text` on both sides. The fields (`(p).a`, `(p).*`, `select * from f()`) and an anonymous record of them (`row((p).*)`) read too (verified, see Notes). Docs only or docs with a clearer error: approaches 1 and 2 of Notes. Docs with a clearer error, approach 2 (the maintainer, 2026-11-24).
- [x] Or read it: `EnableUnmappedTypes()` on the global type mapper changes the whole process (as the Dapper settings in 0096-78), so not that one. An `NpgsqlDataSource` of DbLive's own with `EnableUnmappedTypes()` is another connection pool than the application's with the same connection string: does the enlistment in a `TransactionScope` still give every connection of a transaction the session of the transaction? What would `rows` compare then: the value as `object[]` or as text? Neither works: `EnableUnmappedTypes()` does not read a composite type at all, and a connection of an own data source in the `TransactionScope` gets a session of its own and does not see what the test wrote before it (verified, see Notes). Approach 3 of Notes.
- [x] Do 0096-168 in the same change? The same list of §8.3, and approach 2 gives its types the clearer error too. Yes (the maintainer, 2026-11-24).
- [x] Is `rows-with-schema` of such a column right after the fix (`public.pair` on both sides)? Moot: the value is not read. Of the workarounds, `p::text` is `text` on both sides, `row((p).*)` is `record` on both sides, without the types of its fields, and `(p).*` has the types of the fields (verified).

## Notes
- Found on 2026-11-24 while checking 0096-165 with experiments (a temporary test class, removed).
- Experiments of 2026-11-24 (verified), Npgsql 10.0.1, `postgres:18` in Docker, a temporary test class in `DbLive.PostgreSQL.Tests` (removed). The migration: `create type pair as (a int, b text)`, a table `t (id int, p pair)` with the rows `(1, 'x')` and `(null, 'a "b", c')`, a table `users`, `f_pair() returns pair`, `f_table() returns table (a int, b text)`. Deployed with `DeployParameters.Default`, then `RunTestAsync` of the same builder (the types reloaded by the deployment, 0096-165).
  - Fail, the test gets a `DbLiveSqlException` with the message of Npgsql, without the column: a table column `select p from t`, a value `select row(1,'x')::pair`, `select p::record`, a function that returns the type `select f_pair()`, an array `array[p]` (`... DataTypeName 'public.pair[]'`), a composite inside an anonymous record `select row(1, p)` (`NotSupportedException: Reading isn't supported for record field 1 (PG type 'public.pair' ...`), a whole-row reference `select u from users u` (`... DataTypeName '-.-'`: Npgsql does not load the row types of tables unless `Load Table Composites=true`, with it `'public.users'`, read neither way). The problem of the task is reproduced.
  - Pass: `select p::text` against the text (`rows` and `rows-with-schema`), `(p).a, (p).b` and `(p).*` against plain values (`rows-with-schema` too), `select * from f_pair()`, `select f_table()` (an anonymous record) against `row(1, 'x')`, `select row((p).*)` against `row(1, 'x')`. An anonymous record is read as `object[]` and written as `[1,"x"]`; a field that differs fails with `Expected values: [1,"y"] / Actual values: [1,"x"]`. `rows-with-schema` names it `record`, so `row(1, 'x')` also equals `row(1::bigint, 'x')`.
  - Plain Npgsql on the default data source and on one built with `NpgsqlDataSourceBuilder.EnableUnmappedTypes()`: `GetValue`, `GetFieldType`, `GetFieldValue<object[]>` and `GetFieldValue<string>` of a `pair`, a `pair[]` and `f_pair()` all fail with `InvalidCastException: Reading as '<type>' is not supported for fields having DataTypeName 'public.pair'`. The column schema reads: `DataTypeName = public.pair`, `PostgresType` a `PostgresCompositeType`.
  - A `TransactionScope`: an insert on `new NpgsqlConnection(connectionString)`, then a connection of an own data source with the same connection string: another backend (`pg_backend_pid` 101 and 105), which does not see the insert. A test whose `setup.test.sql` or arrange runs on one data source and whose reader runs on another would not see its own data.
  - The other values that cannot be read fail in `GetValue` with `InvalidCastException` too: a `numeric` `NaN` (`Numeric NaN not supported by System.Decimal`), an `interval` with months (`Cannot read interval values with non-zero months as TimeSpan ...`), a `regclass` (`Reading as 'System.Object' is not supported for fields having DataTypeName 'regclass'`, 0096-168). A composite inside a record fails with `NotSupportedException`.
- How often and how bad: a table column of a composite type is rare; more likely `select f()` of a function that returns a composite type, where `select * from f()` is the usual form, and a whole-row reference. The test fails, so nothing passes by mistake. The cost is the message: it names neither the column nor what to do, and for a row of a table it names the type `-.-`.
- Approaches (2026-11-24, for the maintainer):
  1. Docs only. §8.3 and "How values are compared": a value of a composite type cannot be read (a column, `select f()`, a whole-row reference, an array of it, a composite inside `row(...)`); select it as `text` (`p::text`, `"(1,x)"`), its fields (`(p).*`, `select * from f()`), or `row((p).*)`, compared as the array of its fields. §17: a row for `Reading as 'System.Object' is not supported for fields having DataTypeName ...`. A test in `SqlTestResultSetTests`: the column fails with that message, the three workarounds pass. Small effort, no risk, not breaking, no `MinCompatibleVersion`.
  2. Approach 1 and a clearer error: `PostgreSqlDA.ReadResultAsync` catches `InvalidCastException` and `NotSupportedException` of `ReadValue` and fails the test with the column, the row and the type, as the error of `rows` that cannot write a value: `Cannot read the value of the column 'p' in row 1 of result set 1, of the type public.pair: <message of Npgsql>`, then `Select the value as text in the test.` It covers every value that cannot be read: a composite type, a row of a table, `regclass` and `pg_snapshot` (0096-168), a `numeric` `NaN`, an `interval` with months, an array with a NULL element until 0096-169 reads it. Not `aclitem`: the server fails it (`42883`) before the read. The docs of §8.3 and §17 that quote the messages of `NaN` and `interval` keep them, inside the new message. Effort small to medium (the catch, tests of three types, the docs), low risk. Not breaking: only the text of an error changes. No `MinCompatibleVersion`.
  3. Read the value: not possible with the public API of Npgsql. `EnableUnmappedTypes()` does not read a composite type (above), `MapComposite<T>()` needs a .NET type per composite type. What is left is a converter of DbLive's own through `Npgsql.Internal` (an unstable API) on a data source of DbLive's own. That data source would have to open every connection of DbLive, because of the enlistment above, and then the reload of 0096-165 no longer reaches the connections of the application with the same connection string (its release note, not released yet, says it does). Large effort, high risk. Not recommended.
  - Recommendation: 2. The test already fails; what costs the user time is the message, and one catch makes it say the column and the workaround for all such values at once, also the ones 0096-168 only documents.
- Decision of 2026-11-24 (the maintainer): approach 2, and 0096-168 in the same change.
- Found while doing it (verified on 2026-11-24, Npgsql 10.0.1, a temporary test, removed): a `numeric` beyond `decimal` (`1e40`) fails with `OverflowException: Value was either too large or too small for a Decimal.`, a `date` after the year 9999 or before the year 1 with `ArgumentOutOfRangeException: Value to add was out of range.`, a `timestamp` after 9999 with `InvalidCastException: Out of range of DateTime ...`, so the catch takes any error of the value, not only `InvalidCastException`. `'infinity'::date` and `'infinity'::timestamp` read as the largest value of .NET. `regtype`, `regconfig` and `pg_typeof(1)` read as their OID (`UInt32`, 23 for `integer`).

## Result
- `PostgreSqlDA.ReadResultAsync` reads each value under a catch of any error but `NpgsqlException` (the row is read whole before its values, so an error there is one of the value) and fails with a `DbLiveSqlException`: `Cannot read the value of the column '<column>' in row N of result set M, of the type <type>: <the error of Npgsql>`, then `Select the value as text in the test.`, as the error of `rows` for a value that it cannot write. The result sets are counted in the order of the script, the assert result set included. `rows` and the values it reads do not change.
- Decisions of 2026-11-24 (the maintainer): a clearer error and the docs (approach 2), not a read of the value, which the public API of Npgsql cannot do; 0096-168 in the same change.
- Tests: `DbLive.PostgreSQL.Tests/SqlTestResultSetTests.Test_that_cannot_read_a_value_names_the_column_and_says_to_select_it_as_text`: the message of a composite column; a composite array, a composite inside a record, a function, the row of a table, `regclass`, `pg_snapshot`, a `numeric` `NaN` and `1e40`, an `interval` with months, a `date` after 9999 fail with the column and the type; a composite value on the expected side is in result set 3; `p::text`, `regclass::text`, `(p).*` and `row((p).*)` pass. Before the change the test failed with the error of Npgsql alone (the experiment above).
- Docs: `docs/llms-full.txt` §8.3 (the values that cannot be read, the workarounds, `aclitem`, `regtype`), §17 (one row for the error instead of the rows of `NaN` and `interval`, a row for `aclitem`); `docs/unit-testing/index.md` ("How values are compared"). The release note of 0096-159 quoted the message of an `interval`, which now comes after the new beginning: corrected.
