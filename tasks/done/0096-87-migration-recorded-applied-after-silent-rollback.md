# A script that ends its transaction without an error is recorded as applied

## Release note
**A script that ends the transaction DbLive runs it in now fails the deployment.** A `COMMIT` or `ROLLBACK` in a script that runs in a transaction of DbLive (a migration or breaking script with the default `TransactionWrapLevel: Migration`, a code file, every script under `Deployment`, a SQL test and its `setup.test.sql`) ended that transaction without an error. The rest of the script ran in autocommit mode and stayed committed, and a migration could be recorded as `applied` with only part of it applied, so that the next deployment skipped it. DbLive now compares the ID of the transaction before and after each such script and fails it with its file and `The script ended the transaction that DbLive runs it in: ...`. What the script ran after the end of the transaction is rolled back (on SQL Server DbLive turns `IMPLICIT_TRANSACTIONS` on while such a script runs; on PostgreSQL it adds a check at the end of the command); what its `COMMIT` committed stays. Such a code file is not retried. On PostgreSQL a code file outside the deployment transaction now runs between `begin` and `commit` of its own, as on SQL Server.

To upgrade:
- Remove `COMMIT` and `ROLLBACK` from the scripts that run in a transaction, also `BEGIN; ... COMMIT;` around a PostgreSQL script (`BEGIN` inside a transaction is only a warning there). Such a script deployed before, or failed only after it was recorded as applied; now it fails every time. A migration that must commit by itself gets `"TransactionWrapLevel": "None"` in its item settings file.
- On SQL Server a `CATCH` block that runs `if @@trancount > 0 rollback` and does not rethrow the error now fails the script: rethrow the error with `throw`.
- A SQL test on PostgreSQL that runs `commit;` or `rollback;` passed and left its data behind; it now fails with `The transaction of the test ended before the test did: ...`.
- On PostgreSQL a code file whose only statement cannot run in a transaction block (`create index concurrently`, `vacuum`, a `do` block or `call` that commits) now fails: move it into a migration with `"TransactionWrapLevel": "None"`.

## Problem
On SQL Server a script can end the transaction it runs in without raising an error: `COMMIT` or `ROLLBACK` in the script itself, such as `if @@trancount > 0 rollback` (scripts generated by Redgate tools have it: see Notes). A procedure that ends the transaction of its caller, such as one whose `CATCH` block rolls back and swallows the error, is not silent: SQL Server fails the script with Msg 266 when the procedure returns, and the migration is not recorded as applied; the statements of the script after the call stay committed (verified, `ScriptEndsTransactionTests.Migration_whose_procedure_ends_its_transaction_fails_with_error_266`). `Transaction.Current` stays `Active` then, and the commands after the rollback run in autocommit mode and are committed at once (`MsSqlDA.IsTransactionUsableAsync` documents this; verified for SQL tests in 0096-76 and for failed code files in 0096-61).

Only two callers check for it: `UnitTestItemRunner` after every SQL test, and `CodeItemDeployer` after a code file that failed. Nothing checks after a script that succeeded. Verified on SQL Server 2025 (`ScriptEndsTransactionTests`, see Notes):

- **A migration or breaking script, `TransactionWrapLevel: Migration` (the default).** The statements before the `ROLLBACK` are undone. The rest of the script and `UpdateMigrationStateAsync` run in autocommit mode and are committed. The commit of the scope then fails with the error 3902 (`MigrationDeploymentException` "Unexpected error deploying ..." with `TransactionAbortedException` inside), but `dblive.migration` says `applied`, and the next deployment succeeds and skips a migration that is applied in part.
- **A migration under `TransactionWrapLevel: Deployment`.** The `ROLLBACK` also undoes the rows that this deployment saved for its migrations (`MigrationsSaver`), so `UpdateMigrationStateAsync` finds no row: `MigrationDeploymentException` with `DbLiveMigrationItemMissedSqlException` ("Migration item not found"). The statements after the `ROLLBACK` stay committed, and the next deployment runs the script again on top of them.
- **BeforeDeploy and AfterDeploy scripts, and code files that succeed,** inside the deployment transaction: everything after the `ROLLBACK` is committed (the rest of the script, the code files after it, AfterDeploy, and their rows in `dblive.code` and `dblive.folder_items`), while the deployment fails on its commit with a bare `TransactionAbortedException` (3902) that names no file. A code file that ended the transaction is marked `applied` without its batches before the `ROLLBACK`, and the next deployment skips it by its hash: the objects of those batches are never created.
- **A code file in its own transaction** (0096-83): it fails on `commit transaction` with the error 3902 and is marked `error`, but its batches after the `ROLLBACK` stay committed, and the error does not say what happened. When another file of the round succeeds, the file is retried in the next round on top of what it left, and the error of the retry is the one reported.
- **A script that ends the transaction and opens one of its own** (`rollback; ...; begin tran`, the script leaves it open): SqlClient commits the transaction of the script on the commit of the scope, with the row `applied` in it, and `@@trancount` is 1 after the script. Under `Migration` with `rollback` the deployment succeeds: the statements before the `ROLLBACK` are lost, and nothing says so. With `commit` the deployment succeeds too and everything is committed, but the script and its row are no longer one transaction. Under `Deployment` with `rollback` it fails as without `begin tran`.

With `TransactionWrapLevel: None` a script has no transaction to end, so it is not affected. Neither is a code file with In-Memory OLTP DDL outside the deployment transaction: since 0096-88 it runs without a transaction of its own.

**PostgreSQL is affected too** (verified, `ScriptEndsTransactionExploreTests`, see Notes): a top-level `rollback;` or `commit;` in a script ends the ambient transaction without an error, and the statements after it run in autocommit mode. A migration under `Migration` is recorded as `applied` and skipped by the next deployment, as on SQL Server; the commit of the scope fails with `TransactionInDoubtException` ("This NpgsqlTransaction has completed"). Under `Deployment` a migration fails with "Migration item not found", and a code file with `25P01: RELEASE SAVEPOINT can only be used in transaction blocks`; what ran after the end of the transaction stays. `PostgreSqlDA.IsTransactionUsableAsync` (`select 1`) does not see an ended transaction: `select 1` succeeds in autocommit mode.

It is the only finding of the code review of 2026-11-17 (finding 1) that leaves a database in a wrong state without saying so.

## Fix
One check in `MsSqlDA.ExecuteScriptAsync` covers every caller: when the script runs in a transaction (`Transaction.Current` is set, or `ownTransaction`), read `current_transaction_id()` on the connection of the script before its batches and after them. When the two differ, roll back what is open on the connection and throw a `DbLiveSqlException` that says the script ended its transaction, and what to change in the script: remove `COMMIT` and `ROLLBACK`, or give a migration `TransactionWrapLevel: None`. The query before the script also runs `set implicit_transactions on`, after it reads the ID (with the setting on, the read itself would open a transaction when the one of DbLive is gone already, and the script would run in it unnoticed), and the query after it `set implicit_transactions off`: the statements of the script after the end of the transaction then run in a new transaction, which the rollback undoes, instead of autocommit. Not `@@trancount = 0`: it misses a script that opens a transaction of its own after the end of the ambient one (Problem). The callers already turn a `DbLiveSqlException` into `MigrationDeploymentException`, `FolderDeploymentException` or `CodeDeploymentException` with the path of the file, and do not write the `applied` row.

On PostgreSQL the same check goes to `PostgreSqlDA.ExecuteNonQueryAsync`, when `Transaction.Current` is set, with `pg_current_xact_id()`: the ID is read before the script, and the check is a `DO` block at the end of the command of the script, after `\n;\n`. Its error rolls back the statements that ran after the end of the transaction (Notes, 2026-11-21). `IsTransactionUsableAsync` on PostgreSQL asks `pg_current_xact_id_if_assigned() is not null`, so that `CodeItemDeployer` and `UnitTestItemRunner` see the end of the transaction as on SQL Server (see the questions below).

Both checks also go to `ExecuteQueryMultipleAsync`, which runs the script of a SQL test.

The statements that ran after the `ROLLBACK` are committed and cannot be undone. The fix makes the deployment fail with the file and the cause, and keeps the script from being recorded as applied.

The cost is none: the setting goes into the queries of the ID before and after the script. Decision of the maintainer (2026-11-21): yes, only for a script that runs in a transaction of DbLive. Decision of the maintainer (2026-11-21): yes, after a test confirms it; if it does not, the error of the check is not retried.

- [x] PostgreSQL: does a top-level `rollback;` or `commit;` in a script end the ambient transaction without an error? Not checked. `PostgreSqlDA.IsTransactionUsableAsync` runs `select 1` and sees only an aborted transaction (`25P02`), not one that ended. - [x] PostgreSQL has no `@@trancount`. Compare `transaction_timestamp()` read on the connection of the script before and after it? It is the same value in one transaction, and a later one in the transaction that a command after the end of the ambient one runs in. One more query per script, two in all. It does not depend on the resolution of the clock, and an experiment shows it works under a savepoint (Notes). It assigns a transaction ID to the ambient transaction if it has none yet; a deployment transaction writes the `dblive` tables and gets one anyway. Take it? - [x] PostgreSQL, a code file outside the deployment transaction: it is one command, one implicit transaction. `rollback;` in it ends that transaction: the statements before it are undone, the file is marked `applied`, and the deployment succeeds (verified: `v1` is never created). It is not a transaction of DbLive, like a script under `None`, but the docs promise that a code file is applied as a whole. Leave it, or run such a file between `begin` and `commit` of its own, as on SQL Server, to check it? Decision of the maintainer (2026-11-21): between `begin` and `commit`, as on SQL Server. The file is applied as a whole either way; what changes is a file whose only statement is not allowed in a transaction block (`create index concurrently`, `vacuum`, a `do` block or `call` that commits): it fails now. PostgreSQL has no In-Memory OLTP, so the exception of 0096-88 does not apply.
- [x] `COMMIT` in a script ends the transaction as well. The same error, or a message of its own? Decision of the maintainer (2026-11-21): the same error. The transaction ID does not tell the two apart.
- [x] A code file in its own transaction that ended it: return `CanRetry = false`, so that the next round does not run it again on top of what it left and replace its error? The deployment then fails at once, and the other files of the round are not deployed. Decision of the maintainer (2026-11-21): `CanRetry = false`. After `ROLLBACK` the file leaves nothing and a retry would only fail the same way; after `COMMIT` it would run on top of what the file committed.
- [x] PostgreSQL, SQL tests: a test whose own script runs `commit;` or `rollback;` passes and leaves its data behind, the same bug as 0096-76 on SQL Server (verified 2026-11-17: `insert 100; commit; insert 200;` passes, and both rows stay; with `rollback;` the row 200 stays). ## Result
- **Check.** `MsSqlDA` and `PostgreSqlDA` read the ID of the transaction before every script that runs in a transaction of DbLive (`ExecuteNonQueryAsync`, `ExecuteCodeItemAsync`, `ExecuteQueryMultipleAsync`: migrations, breaking scripts, code files, BeforeDeploy and AfterDeploy and the breaking scripts of the Code folder under `Deployment`, the self-deployment, `setup.test.sql` and SQL tests) and compare it after the script: `current_transaction_id()` on SQL Server, `pg_current_xact_id()` on PostgreSQL. Another ID throws the internal `DbLiveTransactionEndedException`, a `DbLiveSqlException`, which the callers wrap with the file as before. Not for a script without a transaction.
- **Nothing after the end stays.** SQL Server: `set implicit_transactions on` after the read of the ID, off after the script; another ID rolls back the transaction that the statements after the end opened. PostgreSQL: the check is a `DO` block at the end of the command of the script (`\n;\n` before it), with SQLSTATE `DL001`; its error rolls back the implicit transaction of those statements, and a transaction that the script began after the end is rolled back. What a `COMMIT` of the script committed stays: no server lets DbLive forbid it (decision of 2026-11-21: a limit, in the docs; the deployment test finds such a script).
- **PostgreSQL code files** outside the deployment transaction run between raw `begin` and `commit` on the connection, as on SQL Server. `IsTransactionUsableAsync` on PostgreSQL asks `pg_current_xact_id_if_assigned() is not null`.
- **Retries.** `CodeItemDeployer` returns `CanRetry = false` for a file that ended its transaction, in the deployment transaction without asking `IsTransactionUsableAsync`, and outside it after saving the error row; the messages say "The file ended the deployment transaction, so it is not retried." and "The file ended its transaction, so it is not retried."
- **SQL tests.** `UnitTestItemRunner` turns `DbLiveTransactionEndedException` into `TransactionEndedMessage`, whose text now says that what ran after the end is rolled back and names `COMMIT` in a test on PostgreSQL; the check after the test stays. SQL tests on SQL Server compare the transaction ID too (revisits the decision of 2026-11-15 in 0096-76).
- **Tests.** `ScriptEndsTransactionTests` on both providers rewritten for the fix (the exploratory PostgreSQL file removed): migrations under `Migration` with `rollback`, `commit`, `rollback; begin tran`, `commit; begin tran` and, on PostgreSQL, `begin; ... commit;` and a trailing `--` comment; under `Deployment`; a procedure that ends the transaction of its caller; code files in the deployment transaction and in their own; BeforeDeploy; SQL tests on PostgreSQL; `IMPLICIT_TRANSACTIONS` on only for a script in a transaction. `SqlTestTransactionTests` (SQL Server) asserts that only what a test committed stays. Unit tests for `CodeItemDeployer` and `UnitTestItemRunner`. All tests of the solution pass.
- **Docs.** `docs/llms-full.txt` §0 (rule 19, new rule 21), §5.3, §6, §7, §8.2, §10, §13.3, §16, §17, §19; `docs/deployment/migrations.md` ("No COMMIT or ROLLBACK in a script"), `docs/deployment/code.md`, `docs/deployment/index.md`, `docs/unit-testing/index.md`, `docs/unit-testing/deployment-tests.md`.

- 2026-11-21, keeping the statements after the end of the transaction from being committed (verified, both providers of the integration tests, temporary tests, not kept). What can be done is to keep what the script runs after the end from being committed. The table `T` has the row 0; the script is `insert 1; <end>; insert 2;`, in a `TransactionScope`:

  - Left on both: what the script committed with `COMMIT` stays. Only a check of the text before the run could catch it, and it cannot tell a harmful `COMMIT` from a harmless one (`begin tran ... commit` in a script on SQL Server).
- Decision of the maintainer (2026-11-21): DbLive cannot keep a script from ending its transaction, and the docs say so as a limit. The check of the transaction ID before and after a script runs in every deployment, also in production. The deployment test (`DeploymentTest`, `[SqlDeployFact]`) runs the same `DeployAsync`, so it gets the check without code of its own, and it is where such a script is found before the release. It finds a script that ends its transaction on every run; not a `catch` that rolls back only after an error that the production data causes: the check in production is for that case.
- 2026-11-21, considered: a check of the text of a PostgreSQL script before the run. On PostgreSQL only a top-level statement can end the transaction (in a function or a `DO` block it fails with `2D000`), and plain SQL has no `IF`, so every top-level `COMMIT`, `END`, `ROLLBACK` (not `ROLLBACK TO SAVEPOINT`), `ABORT` or `PREPARE TRANSACTION` in a script in a transaction ends it: the check would have no false positives, and it would stop `begin; ... commit;` before anything is committed. It needs a lexer of its own (strings, `E'...'`, `"..."`, `$tag$...$tag$`, nested comments). Decision of the maintainer (2026-11-21): not taken, and no idea file for it. Such a statement ends the transaction on every run, so the deployment test finds it before the release.
- 2026-11-21, `pg_current_xact_id_if_assigned() is not null` on a new connection of the `TransactionScope`, as `IsTransactionUsableAsync` asks (verified, PostgreSQL of the integration tests, a temporary test, not kept): `true` after `pg_current_xact_id()` was read in the transaction, also after an `insert` and under a savepoint; `false` after `rollback;` or `commit;` in a script, also under a savepoint, and twice in a row; `false` in a transaction that has no ID yet (nothing wrote and nothing asked for it), so the check needs the ID read before the script. After an error of the transaction it fails with `25P02`, as before. After `rollback; begin; insert` (the script left a transaction of its own) it is `true`: the check at the end of the command of the script aborts that transaction, and the question then fails with `25P02`.
- 2026-11-21, with the fix (verified, SQL Server 2025 of the integration tests): with `IMPLICIT_TRANSACTIONS ON` SQL Server raises no Msg 266 when a procedure ends the transaction of its caller (`insert 1; exec dbo.Swallow; insert 2;`): the check of the transaction ID fails the script instead, and nothing of it stays (`ScriptEndsTransactionTests.Migration_whose_procedure_ends_its_transaction_fails_and_leaves_nothing`). A code file that outlives `DeploymentTimeout` now fails on the query of the ID after it, on the connection of the transaction that timed out (`DbLiveSqlException` "The transaction associated with the current connection has completed but has not been disposed."), not on the write of its row; the deployment fails with `ExecutionTimeoutException` as before.
- The check by transaction ID makes the fix breaking: a script that ends the transaction and opens its own with `commit` (the third table above: `commit; begin tran;` to commit the progress of a long migration) deploys today and will fail. The same for a PostgreSQL migration in `begin; ... commit;`: today the deployment fails on the commit of the scope after the migration is recorded `applied` with all its statements, and the next deployment goes on; after the fix the migration is not recorded, and the next deployment runs it again. The release note says to remove `begin`/`commit` from such scripts, or to give them `TransactionWrapLevel: None`; `breaking: true`.
