# SQL Server: a SQL test that cannot read a value fails with an error that names neither the value nor what to do

## Release note
**SQL Server: a SQL test that cannot read a value names it and says what to do.** DbLive reads every value of every result set of a SQL test, and SqlClient cannot read some of them: `geography`, `geometry` and `hierarchyid` without the `Microsoft.SqlServer.Types` package in the test project, a CLR type of the user without its assembly, a `decimal` with more than 28 or 29 significant digits. The test failed with the error of SqlClient alone, such as `Could not load file or assembly 'Microsoft.SqlServer.Types, ...'` or `Conversion overflows.`, which names no column. Now it fails as on PostgreSQL: `Cannot read the value of the column 'v' in row 1 of result set 1, of the type decimal(38, 0): Conversion overflows.` and `Select the value as text in the test.` The docs say how to select such values: `.ToString()` of a `geography`, `cast(v as varchar(40))` of a `decimal`. Nothing to change on upgrade.

## Problem
DbLive reads every value of every result set of a SQL test (`MsSqlDA.ReadResultAsync`, `reader.GetValue`), so a value that SqlClient cannot read fails the test, with any assert and without one. The test fails with the error of SqlClient alone: it names neither the column nor what to do. Verified on 2026-11-24 with Microsoft.Data.SqlClient 6.1.4 and SQL Server 2025 (`mcr.microsoft.com/mssql/server:2025-latest`), a temporary test class in `DbLive.MSSQL.Tests` (removed), `select <value> as v;` without an assert:

- `geography::Point(1, 2, 4326)`, `geometry::Point(1, 2, 0)` and `hierarchyid::GetRoot()` without the `Microsoft.SqlServer.Types` package in the test project: `FileNotFoundException`, `Could not load file or assembly 'Microsoft.SqlServer.Types, Version=10.0.0.0, Culture=neutral, PublicKeyToken=89845dcd8080cc91'. The system cannot find the file specified.` The docs name this case (§8.3, §17).
- A `decimal` that does not fit the .NET `decimal` (at most 29 digits): `cast(99999999999999999999999999999999999999 as decimal(38,0))`, `cast(0.12345678901234567890123456789012345678 as decimal(38,38))`, also inside a `sql_variant`: `OverflowException`, `Conversion overflows.` (from `SqlBuffer.get_Decimal`). The docs say nothing of it. A `decimal(38,10)` whose value fits is read.
- `json` and `vector(3)` are read.

Since 0096-166 PostgreSQL fails such a value with `Cannot read the value of the column 'p' in row 1 of result set 1, of the type public.pair: <the error of Npgsql>`, then `Select the value as text in the test.` SQL Server gives no such error, though a test project for both providers meets both.

## Where
- `src/DbLive.MSSQL/MsSqlDA.cs:525` (`ReadResultAsync`, `reader.GetValue`)
- `src/DbLive.PostgreSQL/PostgreSqlDA.cs:482` (`ReadValue` with the catch, the same on PostgreSQL)

## Fix
Read each value under a catch, as `PostgreSqlDA` does, and fail with a `DbLiveSqlException`: `Cannot read the value of the column '<column>' in row N of result set M, of the type <type>: <the error of SqlClient>`, then `Select the value as text in the test.` The result sets counted in the order of the script, the assert result set included. `ExecuteQueryMultipleAsync` lets a `DbLiveSqlException` through as it is (`MsSqlDA.cs:464`).

- [x] Which errors to catch: all but `SqlException`? Npgsql reads the whole row before its values; does SqlClient, without `CommandBehavior.SequentialAccess`, after `ReadAsync` too, so that `GetValue` of a `varchar(max)` of several MB does not read the network? Otherwise a broken connection in `GetValue` reads as an error of the value. Yes: `ReadAsync` without `SequentialAccess` reads the whole row, and `GetValue` of a 50 MB `varchar(max)` returns it after the session was killed. With `SequentialAccess` or a synchronous `Read()`, `GetValue` reads the network and a broken connection fails it with a `SqlException` (verified, see Notes). So all but `SqlException`: a network error would be a `SqlException` anyway.
- [x] The hint for `geography`, `geometry` and `hierarchyid`: as text is `.ToString()`, or the test project adds `Microsoft.SqlServer.Types`. Say both for a `FileNotFoundException` of that assembly, or keep the one line of PostgreSQL? The one line of PostgreSQL (the maintainer, 2026-11-24): the error of SqlClient in the message names the assembly, and the docs name the package.
- [x] A CLR type of the user (`create type ... external name`) without its assembly in the test project: the same `FileNotFoundException`, and is it worth a check (CLR must be enabled on the server)? SqlClient reads `geography`, `geometry`, `hierarchyid` and a CLR type of the user alike: as a UDT (`SqlDbType.Udt`, the case `GetSqlTypeName` already shares), whose .NET type it loads by the assembly-qualified name the server sends. The catch goes by the error, not by the type of the column, so it covers a type of the user without code of its own (from the code, not verified). No test: it needs a compiled assembly, `clr enabled` and a trusted assembly on the server, for the path the `geography` test already takes.

## Notes
- Found on 2026-11-24 after 0096-166: the maintainer asked for the same error on SQL Server.
- The reproduction of `## Problem` holds: `src/DbLive.MSSQL/` did not change since the task was filed (checked on 2026-11-24).
- Experiment of 2026-11-24 (verified), Microsoft.Data.SqlClient 6.1.4, SQL Server 2025 (`mcr.microsoft.com/mssql/server:2025-latest`), a temporary test class in `DbLive.MSSQL.Tests` (removed): `select replicate(cast('x' as varchar(max)), 50000000) as v, 1 as n;` on a connection without pooling, the first row read, then `kill <spid>` from another connection, then `GetValue` of both columns.
  - `ExecuteReaderAsync()` and `ReadAsync()`, as `MsSqlDA`: `GetValue(0)` returns the 50 000 000 characters, `GetValue(1)` 1, the next `ReadAsync` false. The row is read whole before its values.
  - `CommandBehavior.SequentialAccess` with `ReadAsync()`, and the default behavior with a synchronous `Read()`: `GetValue(0)` throws `SqlException: A transport-level error has occurred when receiving results from the server. (provider: TCP Provider, error: 0 - An existing connection was forcibly closed by the remote host.)`. These two show that the experiment tells the cases apart.
- How often and how bad: no operator mistake. A `hierarchyid`, `geography` or `geometry` column without `Microsoft.SqlServer.Types` in the test project is the likely case: `select *` of a table with one (`HumanResources.Employee.OrganizationNode` in AdventureWorks), where the error does not say which column. A `decimal` beyond the .NET `decimal` needs more than 28 or 29 significant digits: rare. The test fails, so nothing passes by mistake; the cost is the time to find the column.
- Approaches (2026-11-24, for the maintainer):
  1. Docs only. §8.3 and "How values are compared": a `decimal` beyond the .NET `decimal` cannot be read (`Conversion overflows.`), select it as text, `cast(v as varchar(40))`; §17 a row for `Conversion overflows.`. Small effort, no risk, not breaking, no `MinCompatibleVersion`. The error still names no column, and a test project for both providers gets two kinds of errors.
  2. The fix of the task. `MsSqlDA.ReadResultAsync` reads each value under a catch of any error but `SqlException` (safe by the experiment above) and throws the message of PostgreSQL; the result sets numbered as in `PostgreSqlDA` (`multipleResults.Count + 1`, the result sets without columns are not counted). The text of the message in one place: a helper in the core that both providers call, instead of two copies. Docs: §8.3 one bullet for both providers (SQL Server: a CLR type without its assembly, a `decimal` or a `decimal` in a `sql_variant` beyond the .NET `decimal`), §17 one row for both, the row of `Could not load file or assembly ...` goes (its text is now inside the new message), "How values are compared". Tests of `## Done when`. Effort small, low risk. Not breaking: the text of an error alone, and the text of SqlClient stays in it. No `MinCompatibleVersion`.
  3. Approach 2, and a `decimal` beyond the .NET `decimal` read as the text of `GetSqlDecimal` (38 digits): such a test passes without a cast. But the JSON of `rows` is then a string for such a value and a number for one that fits, and PostgreSQL fails a `numeric` beyond `decimal` (`1e40`, 0096-166): the providers differ again. More code for a rare value. Not recommended.
  - Recommendation: 2. The same error on both providers, the column named, and the catch is proven not to hide a network error.
- Decision of 2026-11-24 (the maintainer): approach 2, with the one line of the hint.
- Found while doing it (verified on 2026-11-24, Microsoft.Data.SqlClient 6.1.4, SQL Server 2025, a temporary test class, removed), for the docs: SqlClient reads a `decimal` when its digits, without the trailing zeros of the fraction, fit the .NET `decimal`. Read: `79228162514264337593543950335` (`decimal(38, 0)`), `1234567890.1234567890123456789` (29 digits), `0.0000000000000000000000000001` as `decimal(38, 29)`, `0.5` as `decimal(38, 38)` (read as `0.5000000000000000000000000000`, the scale cut to 28), `1.5` as `decimal(38, 30)`, a division and a product of `decimal(38, x)` (the result is `decimal(38, 6)`). Fail with `OverflowException: Conversion overflows.`: `79228162514264337593543950336`, `1234567890.12345678901234567891` (30 digits), `0.00000000000000000000000000001` and `0.12345678901234567890123456789` as `decimal(38, 29)`. `GetSqlDecimal` reads them all. A `rows` test of `cast(0.5 as decimal(38, 38))` against `cast(0.5 as decimal(38, 28))` passes.

## Result
- `MsSqlDA.ReadResultAsync` reads each value under a catch of any error but `SqlException` (the row is read whole by `ReadAsync` before its values, so an error there is one of the value; verified above) and fails with the error of PostgreSQL: `Cannot read the value of the column '<column>' in row N of result set M, of the type <type>: <the error of SqlClient>`, then `Select the value as text in the test.` The result sets are counted in the order of the script, the assert result set included, as on PostgreSQL.
- The text of the error is in one place: `DbLiveSqlException.CannotReadValue` (internal), which `MsSqlDA` and `PostgreSqlDA` call. The public API does not change.
- Decisions of 2026-11-24 (the maintainer): approach 2; one line of the hint, as on PostgreSQL. The docs name the package `Microsoft.SqlServer.Types` as the other way.
- Tests: `DbLive.MSSQL.Tests/SqlTestResultSetTests.Test_that_cannot_read_a_value_names_the_column_and_says_to_select_it_as_text`: `geography`, `geometry`, `hierarchyid` (this test project has no `Microsoft.SqlServer.Types`), a `decimal(38, 0)` and a `decimal(38, 38)` beyond the .NET `decimal` and one in a `sql_variant` fail with the column and the type; the message of a `decimal` in row 2; the error of SqlClient names the assembly; a `hierarchyid` on the expected side is in result set 3; `.ToString()` of the CLR values and `cast(... as varchar(40))` of the `decimal` values pass. Before the change the test failed with the error of SqlClient alone (`## Problem`). All the tests of the solution pass.
- Docs: `docs/llms-full.txt` §8.3 (one bullet for the error of both providers; the SQL Server values that cannot be read, the limit of `decimal`, the workarounds), §17 (the row of `Cannot read the value ...` for both providers; the row of `Could not load file or assembly ...` removed: its text is now inside the new error); `docs/unit-testing/index.md` ("How values are compared").
